## Briefing

### 1. What it is

**HTTP (Hypertext Transfer Protocol)** is the language browsers and web servers use. The browser asks for something ("give me this page"); the server answers ("here it is", or "it moved", or "not found").

**HTTPS** is the same HTTP conversation inside a locked tunnel. The locking is done by **TLS (Transport Layer Security)**.

An analogy: HTTP is sending a postcard. Every post office worker who handles it can read it, and could even change it. HTTPS is sending the same message in a sealed, tamper-proof envelope, after checking the recipient's ID card at the door.

The real meaning: HTTP is a Layer 7, text-based **request/response** protocol, by default on TCP port **80**. HTTPS is HTTP carried over TLS, by default on TCP port **443**. TLS sits between TCP and HTTP and gives three guarantees: **confidentiality** (nobody can read it), **integrity** (nobody can change it unnoticed) and **authentication** (you are really talking to the site you meant).

### 2. Why it exists

HTTP exists because the web needed one simple, shared way to fetch documents and, later, to power every website and API.

TLS exists because **plain HTTP is readable by everyone in the middle**: the Wi-Fi in a café, your ISP, any router on the path. Passwords, card numbers and the **session cookies** that keep you logged in all travelled in clear text. Anyone on the same Wi-Fi could copy them, as the Firesheep incident in lesson 9 showed. TLS solves this by encrypting the connection and by proving the server's identity with a **certificate**.

When it goes wrong, through an old TLS version, an expired or fake certificate, or a page that falls back to plain HTTP, an attacker in the middle can read or change what you see.

### 3. How it works

**Level 1 — a request and a response.** An HTTP request is plain text. It names a **method** (what to do), a **path** (which resource), and **headers** (extra information):

```text
GET /index.html HTTP/1.1          ← method, path, version
Host: example.com                 ← which website (one server can host many)
User-Agent: Mozilla/5.0 …         ← which browser
Cookie: session=8f1c…             ← "this is me, I'm logged in"
```

Common methods: **GET** (fetch), **POST** (send data, such as a login form), **PUT/PATCH** (update), **DELETE** (remove), **HEAD** (like GET, but headers only).

The response starts with a **status code**: a three-digit number whose first digit says what kind of answer it is.

| Code | Meaning | Plain English |
|---|---|---|
| 200 OK | success | "here it is" |
| 301 / 302 | redirect | "it's over there", see the `Location` header |
| 401 Unauthorized | not logged in | "who are you?" |
| 403 Forbidden | logged in, not allowed | "I know who you are; no." |
| 404 Not Found | doesn't exist | "nothing here" |
| 500 Internal Server Error | the server broke | "my fault" |

**HTTP is stateless**: each request stands alone, and the server doesn't remember you between requests. That's why **cookies** exist: the server gives your browser a token after login, and the browser sends it with every later request. Whoever holds that cookie *is* you, as far as the server knows.

**Level 2 — reading headers with curl.** `curl` is a command-line web client. With `-I` it asks only for the headers, which is where most of the security-relevant information lives.

#### Command

```console
$ curl -I http://example.com/
HTTP/1.1 301 Moved Permanently
Server: nginx/1.24.0
Location: https://example.com/

```

#### In simple English

Ask example.com for its home page over plain HTTP, and show only the response headers.

#### Why do I care?

Headers reveal the server software, where you are being sent, and which security protections are switched on. Attackers read them for clues; defenders check them for gaps.

#### Important part

- `-I`: headers only (it sends a HEAD request).
- `301 Moved Permanently`: the site is redirecting you.
- `Location: https://example.com/`: where to, here the **HTTPS** version of the same site. This is good practice: plain HTTP immediately sends you to the encrypted version.
- `Server: nginx/1.24.0`: the web server software and its version. That is useful to an attacker looking for known bugs, which is why many teams hide the version.

#### What should I look for?

The status line and the `Location`. Add `-L` to **follow** redirects, and curl shows each hop:

```console
$ curl -I -L http://example.com/
HTTP/1.1 301 Moved Permanently
Server: nginx/1.24.0
Location: https://example.com/

HTTP/1.1 200 OK
Server: nginx/1.24.0
Content-Type: text/html
Strict-Transport-Security: max-age=31536000

$ curl -L example.com
<h1>Example Domain</h1>
```

The HTTPS reply carries **`Strict-Transport-Security`** (**HSTS**). It tells the browser: "for the next 31,536,000 seconds (one year), only ever contact me over HTTPS, and never accept a plain HTTP version." Without `-I`, curl prints the page itself, called the **body**.

When something is wrong, curl's error tells you *which layer* failed:

```console
$ curl http://nosuch.example/
curl: (6) Could not resolve host: nosuch.example
$ curl http://offline.example.net/
curl: (7) Failed to connect to offline.example.net port 80 after 3 ms: Couldn't connect to server
```

Error **6** is a DNS problem (lesson 5): the name doesn't exist. Error **7** means the name resolved, but nothing answered on port 80 (lessons 3 and 4). A `404` would mean the server answered but has no such page. Three failures at three different layers, and the error tells you which.

**Level 2 — the TLS handshake.** Before any HTTP is sent over HTTPS, the browser and server agree how to encrypt. In TLS 1.3, the current version, it takes one round trip:

```text
 browser                                                   server (example.com)
   │ ① ClientHello: TLS versions, ciphers I support,             │
   │    key share, SNI = "example.com"  ───────────────────────▶ │
   │                                                             │
   │ ◀── ② ServerHello: chosen cipher, key share,                │
   │        certificate for example.com, signature, Finished     │
   │                                                             │
   │ ③ browser checks the certificate; Finished ──────────────▶ │
   │ ════════ encrypted HTTP from here on ══════════════════════ │
```

In plain English: the browser says hello and lists what it can do. The server picks the settings, sends its **certificate** (a digital ID card), and proves it owns that ID. Both sides combine their **key shares** to create the same secret key without ever sending it. From then on, everything (the path, the headers, the cookies, the body) is encrypted.

**Certificates and trust.** A certificate says "this public key belongs to example.com", and it is signed by a **CA (Certificate Authority)**, an organisation your browser already trusts. The browser checks three things: the signature chains up to a trusted CA, the name matches the site, and the certificate hasn't expired. If any check fails, you get a full-page warning. That warning is the browser telling you it might be an attacker.

**Level 3 — what TLS doesn't hide.** In the ClientHello, the **SNI (Server Name Indication)** field carries the site's name in clear text, because the server needs it to pick the right certificate. So an observer can still see *which site* you visit (and its IP), just not *what* you do there. A newer extension, **ECH (Encrypted Client Hello)**, encrypts this too, but it isn't used everywhere yet.

### 4. How attackers abuse it

- **Adversary-in-the-middle.** On shared Wi-Fi, or after ARP or DHCP spoofing (lessons 3 and 6), an attacker sits between victim and website. With plain HTTP they read and change everything. With HTTPS they need the victim to accept a fake certificate, or to be pushed down to HTTP. ATT&CK: **T1557, Adversary-in-the-Middle**.
- **SSL stripping.** The attacker catches the victim's first plain-HTTP request and keeps them on HTTP, while talking HTTPS to the real site themselves. HSTS defeats this.
- **Stealing session cookies.** Any cookie sent over plain HTTP, or readable by page scripts, can be copied and replayed to take over the account.
- **Exploiting old TLS.** Servers that still accept SSL 3.0 or TLS 1.0/1.1, or weak ciphers, are open to known attacks.
- **Bugs in TLS software itself**, such as Heartbleed (see the Debrief).

### 5. How defenders detect it

- **Web proxy and server logs**: methods, paths, status codes and user agents. A burst of 401/403 responses means guessing; many 404s means someone is probing for hidden pages.
- **TLS monitoring**: alerts on expired or self-signed certificates, on unexpected certificate changes, and on clients or servers negotiating old TLS versions.
- **Certificate Transparency logs**: public logs of every certificate CAs issue. Teams monitor them for certificates for their own domains that they never requested.
- **Header scanning**: regularly checking your own sites for missing HSTS, insecure cookies and leaked version banners.

### 6. How to prevent/fix it

- **HTTPS everywhere**, with plain HTTP only redirecting to HTTPS (`301` to `https://`), as example.com does above.
- **HSTS**, and for important sites the **HSTS preload** list built into browsers.
- **TLS 1.2 minimum, TLS 1.3 preferred**; disable old versions and weak ciphers.
- **Cookies with `Secure`** (only sent over HTTPS), **`HttpOnly`** (scripts can't read it) and **`SameSite`** (limits cross-site sending).
- **Automate certificates** (e.g. with the ACME protocol) so they never expire unnoticed, and patch TLS libraries quickly.

### 7. Common mistakes

- **"The padlock means the site is safe."** It means the *connection* is encrypted to *that* site. Phishing sites have padlocks too.
- **"HTTPS hides which sites I visit."** The domain is visible in SNI (and DNS) unless ECH and encrypted DNS are used.
- **Clicking through certificate warnings.** That warning is exactly what an attack in the middle looks like.
- **Testing only the HTTPS site.** If plain HTTP serves real pages instead of redirecting, users can be kept on it.

### Remember it like this

> **HTTP = postcard; HTTPS = sealed envelope with ID check; TLS = the seal. 80 = plain, 443 = encrypted.** Status codes: 2xx ok, 3xx moved, 4xx your problem, 5xx server's problem. HSTS = "always come back over HTTPS."

### Interview answer

> "HTTP is a stateless request/response protocol: methods like GET and POST, status codes like 200, 301, 403 and 404, and cookies to carry sessions. HTTPS runs HTTP over TLS, which provides confidentiality, integrity and server authentication. In the TLS 1.3 handshake, the client and server agree on parameters and derive keys from key shares, and the server proves its identity with a CA-signed certificate. Main risks are adversary-in-the-middle attacks and SSL stripping, which HSTS prevents, plus stolen cookies and outdated TLS versions. I'd enforce HTTPS with HSTS, TLS 1.2 or higher, and Secure, HttpOnly and SameSite cookies, and remember that SNI still reveals the domain."

## Debrief

**What a professional does here.** Before an application goes live, a security engineer checks it like this lab does: headers, redirects, which pages answer without login, which TLS versions are accepted, and how the cookies are set. Penetration testers do the same, from the attacker's side, with permission.

**Real incident: Heartbleed (CVE-2014-0160, April 2014).** OpenSSL, the TLS library behind a huge share of the web's HTTPS servers, had a bug in its **heartbeat** feature, a small "are you still there?" message. The client sends some data plus a number saying how long that data is, and the server echoes it back. OpenSSL never checked that the number matched the real length. An attacker could send 1 byte, claim it was 64 kilobytes, and get back up to 64 KB of the server's memory, over and over. That memory could contain passwords, session cookies and even the server's **private key**, and the attack left no trace in normal logs. Patching wasn't enough: certificates had to be replaced and passwords reset across the internet. The lock was only as strong as the code that built it.

**Key takeaways**

- HTTP = methods, paths, headers, status codes; stateless, so cookies carry sessions.
- HTTPS = HTTP over TLS: confidentiality, integrity, authentication via CA-signed certificates.
- `curl -I` shows headers, `-L` follows redirects; curl error 6 = DNS, 7 = connection refused.
- Defend with HTTPS-only + HSTS, modern TLS, and Secure/HttpOnly/SameSite cookies; SNI still reveals the domain.
